# cashflow-agent

A FastAPI service that categorizes bank transactions and forecasts cash flow.

Transactions arrive with descriptions a human can barely read — `WM SUPERCENTER
#4521`, `SQ *JOES COFFEE`, `PAYPAL *MISCSVC`. The service retrieves similar known
merchants from a Chroma vector store, asks GPT-4o to categorize with that context
in hand, and either saves the answer or routes it to a human depending on how
confident the model is. A separate forecaster projects the balance forward from
transaction history using plain arithmetic — no LLM.

## How a request flows

```
POST /transactions/ingest
   │  writes rows uncategorized, returns a job_id immediately
   ▼
BackgroundTasks ──► dispatcher.categorize_and_apply(ids)
   │                   │  scoped to the batch, never the whole table
   │                   ▼
   │                asyncio.to_thread(categorize_transaction)   × N, bounded
   │                   │  2 embedding lookups + 1 GPT-4o call per row
   │                   ▼
   │                apply_categorization_result()
   │                   │  confidence >= 0.80 → write to the transaction
   │                   │  confidence <  0.80 → leave it, queue for a human
   │                   ▼
   │                DecisionLog row (always, with full reasoning)
   ▼
GET /jobs/{job_id}  →  GET /review-queue  →  POST /review/{id}/approve
```

`GET /forecast` bypasses all of it: no retrieval, no LLM, single-digit
milliseconds.

## Quick start

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env        # then set OPENAI_API_KEY
```

Then seed the data and build the vector index — **in that order**. The app
refuses to start on an empty index (see *Design notes* below), so step 2 is not
optional:

```bash
python -m scripts.generate_synthetic_data --reset   # 1. ~2,600 transactions + 103 vendors
python -m scripts.build_indexes                     # 2. embed the vendor knowledge base
uvicorn app.main:app --reload                       # 3. serve
```

Transactions land uncategorized. To categorize them:

```bash
curl -X POST localhost:8000/categorize/run          # returns a job_id
curl localhost:8000/jobs/<job_id>                   # poll until "complete"
```

That run makes one GPT-4o call per transaction. On a 30,000 TPM account it takes
roughly 40 minutes and a few dollars for the full dataset — the rate limit, not
the code, is the constraint. See `CATEGORIZATION_CONCURRENCY` in `.env.example`.

Full endpoint reference with request/response examples: **[Instructions.md](Instructions.md)**.

## Results

On the bundled synthetic dataset (2,597 transactions, 103 vendors, 14 categories):

| | |
|---|---|
| Auto-applied without a human | 2,529 (97.4%) |
| Queued for human review | 68 (2.6%) |
| Eval accuracy | 100% (150/150) |
| Naive baseline (substring match, no LLM/RAG) | 70.0% |

**The 100% deserves scepticism and gets it in [SKILLS.md](SKILLS.md).** It is
synthetic data scored against labels generated by the same module — a closed
loop. It shows the pipeline is correct on data it was designed for; it says
little about real bank feeds. The 70% baseline is the more informative number:
keyword matching already handles common merchants, and the LLM earns its cost
specifically on the POS-obscured descriptors that baseline cannot touch.

## Design notes

Things that are deliberate, and would otherwise look like oversights.

**The categorizer is synchronous and blocking.** Callers on the event loop must
use `asyncio.to_thread`. Calling it directly once froze the server for 52
minutes during a batch — the categorizer stays pure and sync, and concurrency is
the caller's concern.

**The app won't boot on an empty vector index.** An empty Chroma collection is
otherwise silent: retrieval returns nothing, the prompt still forms, and GPT-4o
answers confidently from general knowledge. The confidence guardrail cannot
catch this, because it measures the *model's* uncertainty, not whether retrieval
worked. Failing at startup is the only thing that makes it visible.

**Vendor descriptions lead with the merchant's literal statement descriptor.**
This is the single biggest lever on output quality — it moved the auto-apply rate
from 69% to 97.4%. Measurements are in SKILLS.md. Those descriptions are never
shown to the LLM; they exist purely as embedding material.

**`dispatcher.py` is named a dispatcher, not a planner.** It is a three-branch
switch with an optional LLM classifier in front. No tools, no loop, no state, no
composition. For three mutually exclusive actions that is the right amount of
machinery, and the honest name avoids a comparison it would lose.

**Eval rows are namespaced `categorizer_eval`.** The benchmark writes decision
rows against real transaction ids; sharing an agent name with production
decisions let an eval run silently empty the human review queue.

## Known limitations

- **Confidence is self-reported by the LLM** and demonstrably not calibrated — it
  takes ten round values, never anything in between. It is the only guardrail.
  Combining it with a similarity floor and retrieval-health checks is the obvious
  next step.
- **`starting_balance` in the forecast is the sum of all transactions**, not a
  real account balance. It implicitly assumes the account opened at zero.
- **Single account, single tenant.** `account_id` exists on the model and nothing
  filters by it.
- **Ingest is not idempotent.** Posting the same CSV twice creates duplicates.
- **SQL and Chroma are separate stores** with no shared transaction, so they can
  drift. Reconcile by comparing the collection count to the categorized row count.

## Layout

```
app/
  main.py            FastAPI app; verifies the vector index at startup
  config.py          settings (model, concurrency, retries) via pydantic-settings
  jobs.py            background job runner, DB-backed (no Celery/Redis)
  observability.py   JSON log formatter
  schemas.py         Pydantic request/response models
  db/                SQLAlchemy models + async session factory
  agents/
    categorizer.py   RAG-grounded categorization + the apply guardrail
    dispatcher.py    intent routing; owns bulk categorization
    forecaster.py    cash-flow projection (no LLM)
  rag/
    vector_store.py  Chroma collections, incremental indexing
  routers/           transactions, categorize, jobs, forecast, review, audit, metrics
scripts/
  generate_synthetic_data.py   dataset + vendor knowledge base
  build_indexes.py             embed vendors and categorized transactions
  build_eval_set.py            sample a fixed, reproducible eval set
  run_eval.py                  score the categorizer against it
tests/                         28 tests, no live API calls
```

## Tests

```bash
pytest
```

28 tests, all offline — OpenAI calls are replaced with fixed
`CategorizationResult` fixtures, and each test gets its own temp SQLite database.
Notable coverage: parallel results staying aligned with their rows, the
auto-apply/queue guardrail, and eval rows never hiding a genuinely queued
transaction.

## Reproducing the eval

```bash
python -m scripts.build_eval_set   # samples 150 rows, writes eval_set.json
python -m scripts.run_eval         # ~150 GPT-4o calls
```

`eval_set.json` is committed so the accuracy number is verifiable rather than
asserted. The deliberately-unresolvable descriptors are excluded from it — they
identify no merchant, so there is no defensible ground truth, and scoring them
would measure guessing rather than accuracy.
